# Анализ задания и границы backend

Источники: «HackAlem AI — Аким на 5 часов», «Датасет районов», «план проекта.pdf», «четкое разделение участников.pdf», предоставленные пользователем. Это учебная симуляция на синтетических данных, не прогноз развития Астаны.

## Принятые решения по расхождениям

- Пользователь уточнил роль: GPT №2 — BACKEND / SIMULATION / INTEGRATOR. Фронтенд и AI-модули принадлежат другим участникам.
- Следуем конкретному распределению: Python, FastAPI, Pydantic, `backend/` и `shared/`. Альтернативный Vite/Node/TypeScript monorepo из раннего плана не создаём.
- Краткое ТЗ описывает пять направлений, а подробный датасет явно разрешает максимум две меры одного направления. Реализуем именно подробные правила: ровно пять решений, минимум три направления как следствие. Пример организаторов с двумя социальными мерами допустим. Трактовку краткого ТЗ команда должна подтвердить у организаторов.
- Исходный AGENTS.md репозитория описывает другое задание про протоколы совещаний. Пользовательское ТЗ имеет приоритет; общие правила качества, изоляции модулей и запрета секретов сохраняются.
- В `feature/ai` уже есть `ScenarioSnapshot` и инъекция `JsonGenerator`. Сохраняем их структуры и не изменяем принадлежащие AI-разработчику файлы.

## Правила

Бюджет 100; остаток не даёт бонуса. Для финализации ровно пять решений; для preview от нуля до пяти. Мероприятие выбирается только один раз, даже в разных районах. Максимум две меры одного направления. Для районной меры требуется действительный район; для городской район отсутствует. Неизвестные ID и запрещённые сочетания отклоняются. Порядок решений не влияет на результат. Невалидный сценарий возвращает причины и `score: null`.

## Формулы

Горизонт H = 8 кварталов. Реализованный эффект: `full_effect * (8 - lag) / 8`. Все эффекты и фиксированные синергии складываются до однократного ограничения каждого индикатора в [0, 100]. Синергии не масштабируются лагом.

Оценка района `D[d] = sum(weight[k] * indicator[d,k])`. Веса T1/T2/E1/E2/S1/S2/B1/B2/C1/C2: 0.10/0.10/0.09/0.11/0.11/0.11/0.09/0.09/0.10/0.10.

`D_avg = sum(population_share[d] * D[d])`.

`Score = 0.7 * D_avg + 0.3 * min(D[d]) - N_crit`, где `N_crit` — число пар район × индикатор со значением строго меньше 40. Значение 40 штрафа не даёт. Промежуточные значения не округляются; все показатели направлены одинаково: больше — лучше.

Контроли: база 52.55768; M7/nura, M8/nura, M10/nura, M12/город, M5/saryarka — стоимость 95, Score 56.54307.

## Синергии и несовместимости

M1 + M2: T1 +2 в районе M1. M10 + M12: B1 +2 в районе M10. M5 + M6: E2 +2 в районе M5.

M1/M3 несовместимы в любых районах. M4/M7 запрещены в одном районе (участок). M5/M13 запрещены в одном районе (дублирование программы).

## API и структура

GET `/api/health`, `/api/districts`, `/api/measures`, `/api/bootstrap`; POST `/api/simulate` (preview), `/api/scenario/finalize`, `/api/recommend`. Типизированный контракт и примеры находятся в `shared/api-contract.md`; OpenAPI генерируется приложением.

`backend/app/models/` — HTTP и внутренние DTO; `backend/app/simulation/` — чтение данных, проверка, эффекты, Score, вклады, рекомендации; `backend/app/api/simulation/` — маршруты и проверка границы AI; `backend/app/main.py` — сборка приложения; `backend/tests/` — тесты; `shared/` — версия данных, контракт и fixtures.

AI объясняет готовые факты. Сервер заново рассчитывает клиентские решения перед AI-анализом и не принимает клиентские цены или Score как истину. Отсутствие провайдера явно обозначается HTTP 503 и не мешает расчётам. Вклад мер учитывает нелинейность штрафов и синергий через Shapley-декомпозицию; сумма вкладов совпадает с изменением Score. Поиск одной замены перебирает допустимые варианты и смену района, но не обещает глобально оптимальный план.

## Проверки

Точные контрольные примеры, все ограничения, каждая синергия и несовместимость, лаги и отрицательные эффекты, границы 0/40/100, перестановки, повторяемость, неизменность датасета, вклады, лучшие замены, HTTP/JSON/OpenAPI, CORS, ошибки AI, совместимость с текущей `feature/ai`, запуск из чистого окружения. Будущие изменения других участников нельзя гарантировать заранее; контракт и повторяемые проверки снижают этот риск.
