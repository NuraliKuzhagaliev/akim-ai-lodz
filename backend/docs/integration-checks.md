## Исправление таймаутов и повторная реальная проверка

Лимиты согласованы: OpenAI SDK — 45 секунд без автоматических повторов, frontend AI-маршруты — 60 секунд, расчётные маршруты — прежние 20 секунд. Исправлено ошибочное сообщение «неверный JSON», когда браузер прерывает чтение тела ответа по таймауту. В SDK это сетевой таймаут, а не абсолютная гарантия длительности запроса. Обе правки находятся в своих feature-ветках: backend PR #3, frontend PR #2; при объединении нужны обе.

После изменения выполнены **5 последовательных реальных запросов** через настоящий frontend `api.analyze()` → Uvicorn/FastAPI → OpenAI `gpt-6-astra` → frontend Zod и нормализатор. Диагностического увеличения таймаута или подставного AI-ответа в этом прогоне нет. Проверены три сценария: официальный, предложенная движком замена и перенос M10 в Сарыарку. Все пять ответов прошли; длительности — **18.95, 18.74, 17.82, 17.98, 17.00 секунды**. Каждый превысил прежний лимит backend 15 секунд. Числовые результаты остались неизменными. Во время генерации отдельный расчёт базового сценария отвечал за **28–46 мс**. Это небольшой функциональный прогон, не нагрузочный тест и не гарантия задержки внешнего API.

Frontend: **26 тестов прошли**, включая ответ AI через 25 секунд, прерывание зависшего запроса через 60 секунд, чтение JSON при таймауте, сохранение сообщения HTTP 503, отсутствие автоматического повторного запроса и очистку таймеров. Backend: реальный SDK с `MockTransport` подтвердил таймаут 45 секунд, ровно одну попытку, безопасный HTTP 503 и работоспособность расчёта после сбоя провайдера. Ключи не включены в опубликованные файлы.

## Первоначальная диагностика и границы проверки

Полный рендер Next.js в этой среде не выполнен: запуск блокируется Windows-ошибкой `spawn EPERM` при создании дочернего процесса. Проверен именно настоящий API-клиент фронтенда по HTTP, а также его runtime-схемы. Визуальную проверку выполняет владелец frontend.

После предоставления ключа выполнена отдельная реальная проверка OpenAI API: доступ к `gpt-6-astra` подтверждён, вызов `/api/ai/analyze` через FastAPI TestClient и настоящий AI-провайдер вернул HTTP 200 за 13.4 секунды. Ответ прошёл Pydantic-модель backend, настоящий `aiResponseSchema` и `normalizeAnalysis()` frontend. Контрольные числа в тексте совпали с серверным расчётом. Ключ в этот коммит не включён.

До исправления первый запрос завершился `APITimeoutError` на старом лимите 15 секунд; следующий диагностический запрос использовал лимит 60 секунд и завершился за 13.4 секунды. Затем лимиты были исправлены и выполнен отдельный прогон из пяти запросов, описанный выше. Мок-тесты по-прежнему используют контролируемый провайдер.

В AI-модуле есть предупреждения об устаревших Pydantic `.dict()`/`.parse_obj()`; на закреплённой Pydantic 2.13.5 они работают. AI-код не редактировался; при миграции на Pydantic 3 его владельцу потребуется заменить эти вызовы.

Docker здесь не установлен, поэтому образ не собирался. В репозитории есть Dockerfile, compose и CI-проверки; локальный Python backend и его HTTP-запуск проверены.

## Перед объединением

Объединять через PR с сохранением текущего main. Feature-ветки frontend и AI добавляют свои директории; backend-папки и shared принадлежат интегратору. Не подключать AI `create_ai_router()` поверх интеграционного адаптера: один и тот же путь появится дважды и обойдёт серверный пересчёт. Сохранить текущие `app.main` и общий контракт.

После объединения: установить backend requirements-dev/requirements-ai и frontend-зависимости; запустить команды README; выставить frontend live-режим; выполнить контрольный сценарий и один реальный AI-анализ с настроенной моделью. Любые изменения данных требуют повторной генерации fixtures и проверки контрольных чисел.
